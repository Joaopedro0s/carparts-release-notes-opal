D1. Explique a metodologia de vibe coding do Opal e compare-a com o pipeline como código da Aula 06: o que é “código”, como é versionado, revisado e testado em cada abordagem?
(96 palavras)
No Opal, vibe coding significa descrever a intenção em linguagem natural e organizar prompts, modelos e conexões no fluxo visual. Nesse contexto, os prompts funcionam como código e o fluxo representa o programa. O histórico do Drive oferece versionamento linear, sem branches, diferenças ou pull requests, enquanto os testes ocorrem manualmente no Preview e no console. Já o pipeline como código mantém Jenkinsfile ou YAML no Git, com revisão por pull request e validação automatizada. Por isso, o Opal acelera a descoberta, mas prompts destinados à produção devem ser versionados, revisados e avaliados automaticamente no repositório.

D2. Descreva a anatomia de um fluxo visual no Opal para gerar release notes a partir de commits: passos, conexões, referências @, assets, modelos e saídas. Justifique a escolha dos modelos.
(100 palavras)
O fluxo começa com um User Input obrigatório para receber commits fictícios. Um asset guarda o guia de estilo. O primeiro Generate, nomeado Classificar mudanças, usa Gemini Flash para classificar rapidamente cada item e produzir uma tabela estruturada. O segundo Generate, Redigir notas, referencia com @ a classificação e o guia, usando um modelo Pro para melhorar precisão e qualidade do texto final. As conexões seguem uma única direção, sem dependência circular. As saídas apresentam uma página com auto-layout e salvam o documento no Google Docs. Flash reduz custo na tarefa simples; Pro é adequado à redação voltada ao cliente.

D3. Quais são os limites do Opal para uso em produção e em que ponto uma equipe deve promover o mini-app para o AI Studio e o repositório?
(94 palavras)
O Opal é experimental e não documenta API pública, webhooks, exportação de código nem hospedagem própria. Seu versionamento é linear, os testes são manuais e existem restrições de conta e governança. A equipe deve promover o mini-app quando a saída alcançar clientes, precisar rodar sem intervenção, envolver dados reais, exigir rastreabilidade ou já demonstrar valor com entradas de referência. Nesse momento, o modelo, as instruções e o formato são fixados no AI Studio, o prompt e o conjunto dourado são versionados no repositório e a esteira passa a executar avaliações, homologação e aprovação registrada.

D4. O Opal se integra ao Drive, Docs, Sheets e ao Gemini. Discuta o risco de shadow IT e proponha uma política de uso para a Carparts.
(95 palavras)
A integração fácil com Drive, Docs, Sheets e Gemini pode criar shadow IT: mini-apps fora do inventário da TI, links públicos esquecidos, prompts com informações sensíveis e soluções sem responsável. A política da Carparts deve permitir apenas dados públicos ou fictícios, registrar dono, finalidade, link, permissões e data de revisão, e proibir acesso de edição amplo. Toda saída destinada a clientes exige revisão humana e aprovação registrada. Cada revisão deve repetir entradas de referência, o compartilhamento do arquivo no Drive deve ser controlado e o uso de produtos experimentais precisa de decisão formal da TI.

D5. Proponha um stage de avaliação de prompt para o pipeline (Jenkins ou GitHub Actions): entradas, critérios, condição de falha, tratamento da chave e controle de custo.
(102 palavras)
O stage recebe o prompt versionado em prompts e pelo menos dez casos do conjunto dourado em eval/golden.jsonl. Cada caso define termos obrigatórios, termos proibidos e, quando aplicável, um esquema JSON válido. O script calcula a taxa de aprovação e encerra com código 1 quando ela fica abaixo de 90 por cento. A auth key permanece em GitHub Secrets com environment ou em credencial do Jenkins, nunca no Git ou nos logs; forks não recebem o segredo. Para controlar custo, o job roda somente quando prompts, avaliações ou código relevante mudam, usa modelo Flash e registra quantidade e custo estimado das chamadas.

D6. Compare Opal, AI Studio (Chat e Build) e Antigravity no ciclo de vida de uma funcionalidade de IA da Carparts, do protótipo à produção.
(103 palavras)
O Opal atende à descoberta: cria rapidamente um protótipo sem código, permite testes com usuários e registra uma ficha técnica com entradas de referência. No AI Studio Chat, a equipe fixa modelo, instruções e saída estruturada, repete os testes e obtém código. O Build gera uma aplicação full-stack, mantém segredos no servidor e pode sincronizar com o GitHub. O Antigravity ajuda a evoluir e manter esse código por meio de alterações revisadas em pull requests. Jenkins ou GitHub Actions executam lint, testes, scan de segredos e avaliação do prompt; somente depois de homologação e aprovação registrada a mesma versão é promovida à produção.
